### 相对申报书的三处方法改进

| # | 改进 | 理由 |
|---|------|------|
| 1 | **建筑高度多源融合**（`data/heights.py`） | OSM 高度标签在成都市中心的覆盖率仅 **1.5–5.4%**（`height`）/ 8.5–19.7%（`building:levels`）。仅用标签会系统性丢弃 80% 以上的高层建筑，使候选集严重偏少。融合四级来源：OSM height → OSM levels×层高 → **CNBH-10m 高度栅格** → 按占地面积的分位数回归填补。每栋建筑记录 `height_source`，供论文报告各来源贡献率与不确定度。 |
| 2 | **地面型候选的建筑覆盖率判据** | 申报书的地面型判据（排除山/水/生态红线 + 坡度≤15°）在成都平原几乎不排除任何单元，会得到约 2300 个候选（≈每个 500 m 格网都是候选）。这不符合实际——建满的老城区没有 1600 m² 空地。补充"建筑基底覆盖率 ≤ β"判据，并对其做敏感性分析。 |
| 3 | **分类别密度稀释** | 屋顶型与地面型是性质不同的设施类别。若按统一质量分在同一池中稀释，地面型（本质是密集的格网中心）会系统性胜出，实测导致**屋顶型候选 100% 被淘汰**，使"屋顶/地面双类别"建模前提在候选阶段即失效。改为：类别内配额 → 类别内最小间距 → 跨类别冲突按单位容量成本裁决。 |

### 论文的两个核心新意（经文献核实为空白）

**(A) 收入分层公平性作为显式优化目标。** 经系统梳理本项目文献库（含 GIS 选址、
UAM 综述、多目标优化共 15 篇），**没有任何一篇**把收入分层公平性作为显式目标。
最接近的 Lu et al. 2025（深圳，*Aerospace* 12(8):709）把公平性放在**筛选阶段**、
优化仍是单目标；Fadhil 2018 则将高收入作为**正向**选址依据，反而加剧不平等。
本研究的公平性目标定义为**最差人群组的平均接驳时间**（`equity_measure:
"group_mean"`），区别于经典 p-中心的单用户 min-max。

**(B) 屋顶型与地面型作为不同成本/容量的设施类别统一建模。** 分层设施已有
先例（NASA Vertihub/Vertiport/Vertistop；Guo et al. 的 Vertipad/Vertibase/Vertihub），
但**从未按"屋顶/地面"这一轴**划分。本研究中两类设施的成本结构相反
（屋顶：无征地、固定成本高；地面：需征地、面积成本高）——见 `costs` 配置。

> 两个新意在论文中的表述红线见第 6 节"诚实的边界"。

| 变量 | 数据源 | 分辨率 | 状态 |

| ↑ 备选通道 | OSM Overpass API（分块） | — | ⚠️ 受限网络下不可用，见下 |
| 建筑高度 | **CNBH-10m**（Zenodo `10.5281/zenodo.7923866`） | 10 m | ✅ 实测可用 |
| 人口 | WorldPop 中国 2020 约束版（主源） | 100 m | ⚠️ 服务器不稳定，见下 |
| 人口（备选） | 建筑体量估计（人均住房面积标定） | 建筑级 | ⚠️ 有循环依赖风险，见下 |
| 高程/坡度 | Copernicus DEM GLO-30 | 30 m | ✅ 实测可用（成都单瓦片覆盖） |

| 路网 | OpenStreetMap | — | ✅ 实测可用 |

### 人口数据源：为什么主源是 WorldPop，备选要慎用

主源是 WorldPop 中国 2020 约束版 100 m 栅格。实测该服务器**不稳定**：
一次 920 MB 的全国文件在传到 55% 时连接中断
（`ChunkedEncodingError: IncompleteRead`），且服务器**忽略 HTTP Range 请求头**，
无法断点续传；中断后还出现过一段时间的 TLS 握手失败。管线对此的处理是
**重试并等待**，而不是自动降级。

降级路径 `population_from_buildings()`（建筑体量 ÷ 人均住房建筑面积）已实现，
但**不是默认值**，原因是**循环依赖**：屋顶型候选来自同一份 OSM 建筑图层，
其高度也来自同一套融合模型。若人口再由建筑体量推算，则"需求"与"供给"变成
同一份数据的两个函数——论文要度量的可达性不平等，就可能只是这个共享来源的
产物，而不是城市的真实属性。因此独立于建筑存量的人口面是值得等待的。

若确实要用备选路径，论文必须报告：标定值（默认 40 m²/人）、该值下的隐含
研究区总人口、以及与七普对应区县常住人口的对比。注意该标定值只影响人口的
**总量标度**，对**空间分布**是中性的（所有单元同比例缩放），而公平性结论
依赖的正是空间分布。

### OSM 数据获取：为什么用 PBF 而不是 Overpass

两条通道都实现了，由 `data.sources.osm_backend` 切换。实测对比：

| 通道 | 来源 | 体积 | 实测耗时 |
|------|------|------|----------|
| Overpass（`data/osm.py`） | overpass-api.de，300 个瓦片 | ~500 MB | **8 小时以上** |
| **PBF（`data/pbf.py`）** | OSM.fr 四川省提取包 | **116 MB** | **18 秒下载 + 41 秒解析** |

Overpass 在受限网络下对同一 IP **强限流**：首个请求返回 200，紧接着的全部
返回 504（响应体仅 695 字节，是限流特征而非查询问题）。而且配置里常见的
备用镜像（kumi.systems、private.coffee）从国内网络**根本连不通**，每次重试
会白等一整个超时周期。PBF 通道一次下载省级快照，还有额外的方法论优势：
它给出的是**某一时刻的完整数据快照**而非逐块抓取的拼接，不存在瓦片边界处
要素被截断的问题，数据时点一致性更强（论文可声明"数据快照 = OSM.fr 提取包
日期"）。

> 踩坑记录：libosmium 在 Windows 上**无法打开含非 ASCII 字符的绝对路径**，
> 而本项目目录名含中文。`pbf.libosmium_path()` 会优先改用相对路径规避——
> 否则会抛 `RuntimeError: Open failed ... unknown error`，报错信息完全看不出
> 是路径编码问题。

### ⚠️ 关于收入代理的重要更正

**Meta Relative Wealth Index (RWI) 不覆盖中国。** 该数据集仅包含 93 个
中低收入国家，中国被明确排除在设计范围之外（2026-09 实测核验 HDX API：
112 个资源中无中国）。任何"用 RWI 表示成都收入"的写法都是错误的。

本项目改用**基于 OSM POI 构成的经济活动指数**（`data/rasters.py::build_poi_economic_index`）：
对 POI 按业态赋权（金融 3.0、写字楼 2.5、高档零售 2.5、酒店 2.0、
餐饮 1.0、生活服务 0.6–0.7），除以单元面积后取对数。

**论文表述红线**：这是"经济活动指数"，**不是收入**。二者高度相关但不等价——
前者度量商业活跃度与业态档次。第 3.5 节（数据）必须说明这一代理关系及其局限，
并用敏感性分析检验结论对该代理的依赖程度。

其他可选路径：`viirs`（夜间灯光，需在 [EOG](https://eogdata.mines.edu/products/vnl/)
注册免费账号后手动下载，程序会自动发现并裁剪）、`local_file`（自备房价或统计年鉴
人均可支配收入数据）。若能用后者获得真实收入分布，新意 (A) 的说服力会显著增强。

## 4.5 三个算法设计陷阱（都曾静默产生错误结果）

这三个问题都不是"写错代码"，而是**设计层面的错误**，且都不会报错——
只会让搜索收敛到一个错误的区域。每一个都是通过与独立实现（pymoo）对照
才发现的，值得在设计阶段就避开。

### 4.5.1 解码器与搜索算子必须分离

**解码器的职责是恢复可行性，不是改善解的质量。**

* **错误一（只补点）**：修复算子只加点不删点，若初始种群稠密，搜索无法删点 →
  实测 100 代内超体积**从未改善**，站点数停在 613–706，前沿成本
  **329–375 亿元**；而整数规划 3.14 亿元即达 96.13 % 覆盖。
  复现：`scripts/25_probe_dense_decoder_defect.py`（约 6 秒）。
* **错误二（解码时剪枝）**：为修错误一，把冗余站点剪枝放进解码器 →
  任何稠密解在评价瞬间被剪回最小覆盖集 → **高站点数区段完全无法探索**。
  与 pymoo 对照，超体积只有其 **18%**。

最终方案：解码器只补点；剪枝改为**按概率作用于部分子代**的局部搜索算子。
同一实现超体积达到 pymoo 的 **153%**。

### 4.5.2 初始种群必须覆盖站点数的合理全区间

修复算子只加点，因此初始种群的**规模谱**决定了搜索能到达的区域。
若全部个体从同一规模出发，搜索被永久限制在窄区间。改为在对数尺度上
从 `[12, 400]` 抽取各不相同的站点数（`stage4_nsga2.init_site_range`）。

### 4.5.3 固定规模模式下所有算子都必须保规模

固定 N 时，"每个方案恰含 N 个站"是硬前提。任何会改变站点数的算子都会
破坏它，包括：

* 通用修复算子（覆盖不足时加点）→ 改用**保规模修复**（`make_fixed_cardinality_repair`，用"换点"代替"加点"）
* 剪枝局部搜索（只删点）→ 固定规模模式下**必须禁用**（`nsga2_core` 已加防线，调用方忘记关闭也不会出错）
* SBX 交叉（子代规模自由漂移）→ 改用**保规模杂交**（`crossbreed_masks`，从父代并集中抽取 N 个）

`scripts/10_scheme_family.py` 会**校验**每个解的站点数是否等于 N，
不相等时明确报错而不是静默通过。

## 5. 关键实现说明

### 5.1 NSGA-II 为什么自己实现

申报书把 NSGA-II 编码列为项目任务。从零实现（`nsga2_core.py`）便于掌握
每个算子、在答辩中解释清楚，并支持本研究需要的**结构性约束修复**
（`make_repair`：贪心补足未覆盖的核心需求）。同时提供 pymoo 交叉验证
（`--validate-nsga2`），报告两种独立实现的前沿质量比值——这是论文附录中
增强结果可信度的细节。

### 5.2 编码等价性

申报书表述为"以起降场编号为基因进行整数编码"。实现采用**等价的 0/1 掩码编码**
（维度 = 候选数，`x_j=1` 表示在候选 `j` 建站）。掩码中 1 的位置即所选编号，
两种编码在解空间上一一对应；掩码编码可直接使用标准算子（SBX/多项式变异），
避免变长整数编码的重复基因与非法解问题。论文中应说明该等价性。

### 5.3 容量约束的边界（务必在论文中如实披露）

`stage3_ip` 中的容量约束形式为 `ℓ_j · y_j ≤ q_j`，其中 `ℓ_j` 是**预计算的常数**
（按"就近分配"估计的负载上界），而非决策变量。因此它是一个
**选址可行性筛选**——排除自身负载超容量的候选点——**并不能让需求在站点间
重新分配**。若论文要主张"负载均衡"，必须扩展模型引入 `x_ij` 变量；
否则应明确声明该约束的作用范围。

### 5.4 NSGA-II 侧无设施数上限

IP 情景有 `Σy_j ≤ N_max`，而 NSGA-II 的四个目标中没有设施数约束
（成本目标隐含地限制了站数）。第 5.5 节将两者对比时，必须声明这一差异是
**设计选择**而非疏漏。

### 5.5 `min_core_demand` 的两种口径

数值在 `0–1` 之间解释为**分位数**（推荐，`0.6` = 需求量最高的 40% 单元必须
被覆盖）；`≥ 1` 解释为**绝对量**（次/日）。推荐分位数：绝对阈值与出行生成率
标定强耦合，换城市或换出行率就会让核心单元变成空集（**覆盖约束静默失效**）
或全集（失去优先级区分）。程序在核心单元为 0 时会显式告警。

## 6. 诚实的边界（论文必须如实说明）

1. **地面型候选不是真实地块**。位置取 500 m 需求栅格的中心，单元作为地块代理
   （250 000 m² ≫ 1600 m² 最小要求）。真实的地块边界、权属与现状用地未体现在
   候选几何中。若后续能获取地块级数据，可直接替换
   `build_ground_candidates()`。
2. **收入是代理变量**，非真实收入。见第 3 节。
3. **接驳时间为自由流欧氏近似**。`travel_time_matrix` 用直线距离除以方式速度，
   未考虑路网绕行。`geo.network_travel_time_matrix` 已实现基于 OSM 路网的最短路，
   但默认未启用（耗时较长）。这是本方法相对 *CEUS* / *JTG* 级别期刊的主要短板，
   也是投稿前的优先改进项。
4. **单一案例城市**（n=1），结论的可迁移性需在其他城市验证。
5. **建筑高度含不确定性**。融合后各来源的 `height_sigma_m` 已记录，
   敏感性分析应检验候选集对高度误差的稳健性。

## 9. 三维可视化（CesiumJS）

```bash
python scripts/export_3d.py --data-mode real   # 导出 viz3d/evtol_data.js
python viz3d/start_3d.py                       # 起本地 HTTP 服务并打开浏览器
```

**不能直接双击 `chengdu_evtol_3d.html`**：Cesium 要通过 XHR 读取同目录的
`evtol_data.js` 与 `cesium_token.js`，`file://` 协议下会被浏览器同源策略拦截，
表现为白屏且控制台无明显报错。`start_3d.py` 会起一个只监听本机的静态服务
再打开页面。

### Cesium ion token 需自备

三维地球的地形与建筑底图来自 Cesium ion（World Terrain + OSM Buildings），
需要一个免费 access token。**本仓库不含任何 token**——它属于个人凭证，
不随代码分发。启用步骤：

1. 到 <https://ion.cesium.com/tokens> 创建 token（免费）；
2. 在 `viz3d/cesium_token.local.txt` 写入该 token（单独一行，无引号、无其他内容）；
3. 生成浏览器可读的 JS：
   ```bash
   python scripts/export_3d.py --token-only
   ```

`cesium_token.local.txt` 与生成的 `cesium_token.js` **请勿提交到版本库或公开分享**。
页面在缺少 token 时会显示明确提示与创建链接，而不是白屏。
